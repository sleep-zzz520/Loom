# Loom 架构

## 目标

一个 App 包含所有模块：待办、日历、备忘录、邮箱、Agent、音乐、个人资料、设置。本轮先搭建 Loom 的统一桌面框架，后续模块按迭代逐个接入。

## Agent 最终目标（产品定义）

Agent 不是等待用户提问的聊天工具，而是持续运行在 Loom 之上的主动智能中枢。聊天只是它的一个交互入口，不是 Agent 的全部形态。

Agent 需要持续结合时间、待办、日历、备忘录、资料库、个人资料、长期规则和用户行为，在合适的时机主动发现值得处理的事情，并主动提醒、建议、规划和跟进。例如：发现任务长期未推进、临近日程时整理准备材料、发现资料与待办之间的关联、在用户表达未来意图后于合适时间继续跟进。

目标工作流：

```text
时间节点 / 数据变化 / 用户行为 / 已知目标
                    ↓
             Agent 汇总工作台上下文
                    ↓
            判断现在是否值得打扰用户
                    ↓
         主动提醒、建议、计划或生成行动卡片
                    ↓
       按权限直接执行，或等待用户确认后执行
                    ↓
             记录结果，并继续跟进后续变化
```

设计边界：

- Agent 应该主动，但不能制造噪音；需要结合免打扰时段、提醒频率和重要性判断是否打扰用户。
- 读取和分析工作台信息是默认能力；新增、修改、删除等有副作用的操作默认需要确认，后续再通过明确的权限设置开放安全的自动执行范围。
- 每次主动行为都应能解释触发原因、使用了哪些上下文以及执行了什么动作，并保留后续跟进状态。
- 主动提醒服务只是基础设施；当前 `notifier.cjs` 对截止时间和重要日期的规则检查不等于最终的主动 Agent。主动运行基础设施已拆分到 `proactive.cjs`，目前支持每日简报、数据变化后的事件跟进、目标关联与跟进记录。细粒度自动执行权限和外部事件源仍需后续单独开放。

当前主动运行闭环：

```text
应用运行
  ├─ 每 60 秒检查一次每日简报（每天最多一次）
  └─ 待办 / 备忘录 / 资料库 / 分类发生变化
       ↓
     15 秒合并窗口，避免连续编辑产生噪音
       ↓
     只读读取工作台上下文，事件跟进每天最多三次
       ↓
     生成主动建议（必要时附带待办提案），写入建议队列并按免打扰与每日上限送达
```

最终定位：其他模块负责承载数据和具体行动，Agent 负责持续感知、理解上下文、主动判断并推动用户完成事情。

主动建议的行动闭环：

```text
主动建议附带明确的下一步
  → Agent 页面展示“安排为待办”
  → 用户打开确认卡片并确认
  → 主进程重新校验提案后写入待办
  → 建议标记为“已安排”，保留运行与建议记录

用户也可以从主动建议的更多操作中选择“明天上午再看”；建议会保留在本地，但在 `followUpAt` 到达前不会再次出现在当前建议队列，到点后会按免打扰和每日上限发送一次桌面跟进提醒，再回到待处理队列。Agent 主动提醒与待办/重要日期提醒共用 `notificationHistory` 计数，避免超过同一套每日上限。

每条主动建议也会持久化为一条 Agent 主动消息。消息以未读入口出现在会话菜单；打开它会创建或继续对应会话，并将这条内容作为普通 `assistant` 消息显示。用户的后续回复会携带该消息上下文继续同一对话。桌面通知点击会直接打开对应的主动消息；延后建议到期后会再投递一条同一线程的跟进消息。

当用户要求沉淀长期信息或可复用流程时，Agent 只会生成“候选记忆”或“候选 Skill”确认卡片。确认后它们仍处于候选状态；用户在 Agent 页面审核采纳/启用后才会进入后续上下文。替换旧记忆或 Skill 时，旧版本会被可恢复地归档，避免模型无审批改写长期规则。
```

主动检查仍然只读；提案不会在后台直接写入数据。

## 目标、记忆与 Skill 闭环

```text
用户确认创建持续目标
  → 待办或主动建议可关联目标
  → 待办完成、建议已安排、手动跟进结果会同步行动状态
  → 页面基于有效行动计算目标进度，并保留已忽略/移除/完成的记录
  → 用户确认目标完成时可记录结果；完成目标可重新跟踪，归档目标可恢复

用户确认候选记忆 / 候选 Skill
  → 页面审核采纳、启用、丢弃或归档
  → 已审核记忆按相关性检索；已启用 Skill 只在当前任务命中时加载
```

目标和跟进数据由 `electron/agent-state.cjs` 统一校验和持久化。待办的 `agentGoalId` 连接目标与具体行动；主动建议的 `goalId` 可由 Agent 生成，也可在页面中手动关联。目标归档会保留历史记录；记忆和 Skill 的归档可在页面恢复，且在归档期间不会进入 Agent 上下文。

OpenClaw 与 Hermes 的参考结论和落地映射见 [Agent 参考项目与架构决策](AGENT_REFERENCES.md)。

## 分层

```text
React 页面组件（src/modules/*）
        │ window.workbench.*
        ▼
Electron 预加载桥（electron/preload.cjs）
        │ IPC
        ▼
主进程服务（electron/main.cjs 注册 IPC）
        │
        ▼
本地数据层（electron/store.cjs）
        │
        ▼
JSON 文件（系统用户数据目录 / workbench-data.json）
```

渲染进程不直接访问 Node，所有数据读写通过 `window.workbench.data.*` 调用 IPC。

## 模块约定

每个模块 = 页面组件 + 数据 key + IPC 接口：

1. 页面组件放在 `src/modules/<Module>.tsx`。
2. 在 `src/App.tsx` 的侧边栏数组注册菜单项。
3. 数据写入 `store.cjs` 的 `modules.<key>`；新增模块只需在默认数据里预留一个 key，页面通过通用接口 `getModule(name)` / `setModule(name, items)` 读写。

当前预留数据 key：

| key | 用途 |
| --- | --- |
| `modules.todos` | 待办 |
| `modules.events` | 日历事件 |
| `modules.notes` | 备忘录 |
| `modules.profileItems` | 个人资料条目 |
| `modules.categories` | 资料自定义分类 |
| `modules.agentRuns` | Agent 主动运行记录 |
| `modules.agentSuggestions` | Agent 主动建议队列 |
| `modules.agentMessages` | 可回复、可追踪已读状态的 Agent 主动消息 |
| `modules.agentGoals` | Agent 持续目标 |
| `modules.agentGoalActions` | 目标关联的待办、建议与手动跟进行动 |
| `modules.agentMemories` | 候选、已审核和已归档的长期记忆 |
| `modules.agentSkills` | 候选、已启用和已归档的可复用 Skill |

`settings` 包含 `profile / email / netease / notify / agent / sync` 分组。邮箱连接信息保存在 `settings.email`；授权码仅由主进程处理，经 Electron `safeStorage` 加密后写入本地数据文件，通用数据 IPC 会清空该字段，渲染进程不能再读取已保存的密码。`settings.agent.persona` 保存 Agent 名字、基础人格、主动沟通方式和用户补充的长期合作约定；它会同时进入普通聊天、后台主动检查、主动消息和桌面通知的呈现，但不能覆盖事实校验、数据确认或权限边界。`settings.agent.proactiveEnabled` 控制主动检查、跟进提醒和桌面送达；关闭后保留已有建议与运行记录，但不再启动新的后台主动运行。`notify` 中的截止提醒档位、免打扰时间、每日上限与重要日期由主进程通知服务每分钟读取一次；已发提醒（包括 Agent 主动提醒）记录在 `modules.notificationHistory`，用于重启后的持久去重与每日上限统计。

Agent 页面会通过右上角会话面板读取 `modules.agentRuns`，展示最近主动检查的状态、触发来源、读取的上下文、判断摘要与送达结果；该记录区默认折叠，不参与主聊天画布，也不会改变主动检查的调度逻辑。未读的 `modules.agentMessages` 会在同一会话菜单中以“主动消息”入口呈现；打开后会进入对应聊天线程，并同步标记消息和关联建议为已读。聊天主画布只承载消息流和输入框；右上角的“管理”抽屉集中承载目标进度、关联行动、结果记录、主动建议、最近处理、记忆与 Skill 审核，避免把工作流管理内容混进对话。

Agent 是工作台的控制台：模块需要将可读取能力和可执行能力明确注册为 Agent 工具，由主进程执行受限操作，再通过预加载层把类型化 UI 命令送回渲染进程。不要让模型直接拼接 IPC 通道、访问本地文件或持有外部服务凭据。当前 Agent 运行时可读取目标、已审核记忆和相关 Skill；目标、候选记忆与候选 Skill 都只能经确认卡片写入。音乐模块除 `search_music` 与 `play_music` 外，已接入 `get_music_library` 与 `get_music_playlist`：Agent 可读取已同步账号、歌单和曲目，并按需同步用户指定歌单以分析偏好。用户询问自己的音乐偏好时，运行时会在模型生成前刷新歌单目录，并预读取最多两张代表性歌单及其曲目样本，避免模型因漏调工具而误答“没有记录”；回复必须说明分析样本的边界。后台主动检查只读取缓存，不会静默同步整张歌单。搜索结果会同步给 Agent 和音乐页；只有用户明确要求播放时，Agent 才会请求播放链接并命令音乐页开始试听。后续模块沿用这一“工具定义 → 主进程校验/执行 → 类型化 UI 命令”的接入方式。

Agent 会话首条用户消息会生成本地摘要作为默认标题；占位标题只会在仍未手动命名时自动替换。会话历史支持行内重命名，名称与会话消息一起持久化到 `modules.agent`。

## 音乐第一期

音乐模块通过主进程访问兼容 NeteaseCloudMusicApi 的服务；默认依赖随桌面端安装，并由 Electron 主进程在工作台启动时自动拉起、退出时关闭，用户不需要先打开网页或手动启动服务。设置中的 `settings.netease.apiBase` 保留给需要接入自定义兼容服务的高级场景。渲染进程只通过预加载层调用音乐 IPC，不接触账号会话凭据。当前支持公开歌曲搜索、热门搜索词和应用内试听，也支持通过 `/login/qr/key`、`/login/qr/create`、`/login/qr/check` 完成二维码登录，通过 `/login/status`、`/user/playlist` 同步账号与歌单元数据，并在选择歌单时通过 `/playlist/track/all`（旧服务回退到 `/playlist/detail` + `/song/detail`）同步歌曲列表。会话凭据只保存在主进程的应用用户数据目录中，页面只读取脱敏后的账号、歌单和歌曲数据。当前不包含下载、歌词或绕过版权限制；播放链接不可用时会提示用户检查服务、登录状态或版权限制。

## 邮箱第一期

邮箱页面通过 electron/mail.cjs 在主进程连接通用 IMAP / SMTP 服务。渲染进程只可调用受限的账户保存、连通性检查、文件夹与邮件读取、已读标记和发信 IPC，不能直接建立网络连接或读取已保存的授权码。

当前支持：

- 配置 IMAP / SMTP 主机、端口、TLS 开关与邮箱账号，并分别验证收信、发信连通性。
- 读取文件夹和最近 50 封邮件的邮件头；打开邮件时标记为已读，并以纯文本显示正文，避免直接执行不可信 HTML。
- 发送纯文本邮件，并在回复时携带 In-Reply-To 关联标识。

当前不支持 OAuth2、多账户、邮件搜索、移动/删除邮件和附件下载。为保护本地内存，邮件正文源暂限制为 2 MB；后续需要完整大邮件或附件下载时，应改为 IMAP 与 MIME 流式读取。

## 如何新增一个模块

1. 在默认数据里增加 `modules.<key>` 初始值。
2. 新建 `src/modules/<Module>.tsx`，通过 `window.workbench.data.getModule('<key>')` 读取、`setModule('<key>', items)` 写入。
3. 在 `src/App.tsx` 添加菜单项，并把占位页替换为真实组件。
4. 为需要主进程能力的模块（邮箱、网易云、Agent、通知、同步）在 `main.cjs` 注册专用 IPC，并在 `preload.cjs` 暴露类型化接口。

## 已知边界

- 当前本地数据为 JSON 文件，单用户、单进程场景足够；后续可平滑迁移到 SQLite，IPC 接口保持不变。
- 模块写入采用整数组替换，未做并发合并；主窗口单实例场景下没有冲突。
- 主动提醒仅在桌面应用的主进程仍运行时触发；若需要应用完全退出后也准时送达，需要另行接入本机后台调度或同步服务。
